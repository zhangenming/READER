## 结论一：无环是真的，但它靠的是一个「反转数据流的单例」

`tmp/verify-模块图.mjs` 三色 DFS 实测通过：**0 个 import 环**。但同一套扫描暴露出 import 图看不见的另一半：

`js/状态.js` 是被 **21 个模块** import 的共享可变单例，含 94 个被读写字段。对每个 `状态.<字段>` 做「写方层级 vs 读方层级」比对（`tmp/arch-隐藏数据耦合.mjs`）：

| 指标 | 值 |
| --- | --- |
| 向上数据耦合（读方层级 **低于** 写方层级） | **90 条** |
| 涉及读方模块 | 19 个 |
| 涉及共享字段 | 34 个 |
| 写方层级分布 | L12 `app.js` 60 条 · L8（字体设置/自动滚动/查找弹窗）24 条 · L11 正文交互 5 条 · L7 跳转动画 1 条 |
| 这些读方是否 import 了写方 | **全部为「否」**——低层模块结构上不可能 import 高层 |

置信度 high（每条都能定位到具体 `状态.x =` 赋值处）。典型例子：

- `状态.行高`：由 `js/字体设置.js`(L8) 写入，被 `js/指示器.js`(L6)、`js/跳转动画.js`(L7)、`js/滚动条.js`(L5) 读取。
- `状态.自动滚动速度`：由 `js/字体设置.js`/`js/自动滚动.js`(L8) 写入，被 `js/滚动条.js`(L5) 在剩余时间算法里读取（`js/滚动条.js:249,253`）。
- `状态.文本` / `状态.文件名`：由 `app.js`(L12) 写入（32 处写入点），L1–L9 共十余个模块读取。
- `状态.渲染起点`：`js/虚拟渲染.js:78` 与 `js/排版引擎.js:463,501` 都写入，`js/自动滚动.js:615` 读取。

**解读**：DAG 之所以能保持无环，恰恰是因为 app.js 作为 composition root 把跨层通信全部改走「写 `状态` → 别人读 `状态`」和回调注入两条旁路。编译期耦合低，运行期耦合高。任何只看 import 图的评估都会严重低估这里的连接密度。

推论（置信度 medium，未做运行时测量）：这 90 条边没有类型或命名约束保护，字段改名或删除只会在运行期表现为「读到 undefined」，而不是启动报错。`js/状态.js` 已有 JSDoc 标注是主要缓解手段。

## 结论二：`app.js` 是全系统唯一的「高扇出 + 零被依赖」节点，也是最脆的一根线

`app.js`：fanOut **26**（31 个模块里连了 26 个）、fanIn **0**、爆炸半径 **0**、I = 1.0、1187 行。同时它独占 L12。

- 半径 0 是好消息：改 `app.js` 不会让任何模块**编译失败**。
- 半径 0 是坏消息：那 3 处断环注入（`app.js:346` 右下控件、`:395` 滚动条拖拽、`:398` 跳转动画）一旦被删或漏调用，对应模块**照常加载、静默失效**，没有任何 import 错误或启动异常会提示。参见证据底稿「断环机制」。
- 加上它是 60/90 条向上数据耦合的写方——`app.js` 同时是装配中心、状态写入中心和断环中心。

## 结论三：`js/常量.js` 和 `js/状态.js` 是稳定的核心，这是好事，但边界不同

按 Martin 不稳定性指标 I = fanOut/(fanIn+fanOut)，两者 I 接近 0，即**高度稳定**，且爆炸半径最大（29 / 22，几乎全图）。「稳定且被广泛依赖」符合良好抽象方向，不应作为缺陷处理。区别在于：

| | `js/常量.js` | `js/状态.js` |
| --- | --- | --- |
| 半径 | 29（= 全部 30 个其他模块，仅 `js/阅读统计.js` 不依赖它） | 22 |
| I | 0.00（fanOut 0） | 0.04 |
| 性质 | 197 行不可变常量 → **稳定的抽象**，健康的公共核心 | 381 行可变单例 → **稳定的实现**，改动即全量回归 |

即：动 `常量.js` 的值语义要全员回归，但它本身不会引入耦合；动 `状态.js` 的字段名/结构则在上面 90 条隐藏边上无声扩散。

## 结论四：真正值得警惕的三个节点——既不稳定又被广泛依赖

`violations.csv` 里 `unstable_shared`（I > 0.5 且 爆炸半径 ≥ 8）命中 3 个，这是教科书式的「不稳定抽象被依赖」反模式：

| 模块 | 层 | fanIn | fanOut | I | 半径 | 行数 |
| --- | --- | --- | --- | --- | --- | --- |
| `js/滚动条.js` | L5 | 4 | 6 | 0.60 | 11 | 260 |
| `js/面板.js` | L5 | 3 | 4 | 0.57 | 11 | 181 |
| `js/跳转动画.js` | L7 | 6 | 7 | 0.54 | 8 | 440 |

注意半径(11) 远大于直接 fanIn(4/3)：说明是**传递**依赖把它们挂在了主链路上，而不是有人直接大量 import 它们。它们处在 `虚拟渲染`/`排版引擎` 通往 `自动滚动`/`键盘控制` 的必经位置。

## 结论五：L0–L12 是「最长路径深度」，不是架构分层——不要据此立规矩

144 条边里 **108 条（75%）跨越 1 层以上**。这意味着所谓 13 层只是深度度量，不构成层次约束；拿它当分层治理基线（比如写「禁止跨层 import」规则）会立刻产生 108 条误报。`violations.csv` 中 `cross_level` 行因此显式标注 `层级为最长路径深度而非语义分层；跨层本身不是缺陷`。

按 import 图能得到的**真实**分组只有两条线：`js/` 29 个功能模块 + 根级 2 个入口（`app.js`、`语音订阅.js`），且 `语音订阅.js` 与主链路完全隔离（只 import `常量.js`，半径 0）。
