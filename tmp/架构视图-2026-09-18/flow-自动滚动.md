## 移动的东西是什么

这条流程里流动的是**一个亚像素级的浮点滚动位置**：`自动滚动状态.浮点位置`。
它不由滚动事件驱动，而由 rAF 自续驱动；每帧积分一次，再被拆成「整数部分写 `scrollTop` + 小数部分写合成层 `transform`」两路落地。
理解这张图的关键是：**位置积分跑在屏幕刷新率，而决定速度的反馈环路只跑在 20Hz。**

## 主路径（① → ② 循环）

启动：悬停/聚焦滚动按钮（`app.js:418-419`）或键盘（`js/键盘控制.js:190/236/406/157`）→ `js/自动滚动.js:233` → `:239-249` 抢占旧 rAF → `:251-274` 建状态 → `:275` 挂首帧。

建状态时有三个决定性动作：`当前速度` 从 **0** 起步（`:256`，所以是缓动加速而非突跳）、`浮点位置` 从 `scrollTop` 取齐（`:257`）、`最大滚动位置` **一次性缓存**（`:272`）。最后一项是本项目明确的性能取舍，源码注释（`:271`）写着「滚动中画布高度不变，避免在每一帧读取布局尺寸触发同步重排」。

每帧 `执行自动滚动(当前时间)`（`:522`）：

| 步 | 位置 | 动作 |
| --- | --- | --- |
| 1 | `:529` | `经过毫秒 = min(50, Δt)` —— **掉帧钳制**，防止切回标签页时一次跳一大段 |
| 2 | `:530` | `缓动比例 = 1 - exp(-Δt/140)`（`自动滚动缓动时长=140`，`常量.js:44`） |
| 3 | `:534-538` | 选目标速度：快速翻页 → 固定高速；停留中 → 0；否则 → `密度目标速度` |
| 4 | `:550-552` | 速度指数插值 → 位置积分 `+= v*Δt/1000` → `clamp(0, 最大滚动位置)` |
| 5 | `:583` | **唯一每帧写入点**：`scrollTop = 新位置`（整数 px） |
| 6 | `:584` | 节拍门：距上次界面时间 ≥ 50ms？ |
| 7 | `:613-615` | 回读被浏览器取整的 `scrollTop`，算出 `小数位移`，写 `transform: translateY(...)` |
| 8 | `:616` | `更新滚动块位置(缓存的视口度量, 浮点位置)` |
| 9 | `:617-621` | 到文末则停止并 return；否则 `:621` 自挂下一帧 |

第 7 步是这条链路最精巧的地方，注释在 `:611-612`：Chrome 的 `scrollTop` 按整数存储，低速时若不补小数，位置要累计满 1px 才产生一次可见移动，观感就是「一顿一顿」。于是每帧先写整数、再回读、把差额用**合成层**补掉——绕开布局，不触发重排。

## ③ 50ms 界面节拍：唯一的布局读取窗口

只有节拍门打开时才做重活（`:587-609`）：读 `clientHeight`/`scrollHeight` → `:593` 刷新 `最大滚动位置` → `:594` 算 `密度目标速度` → `:598` 更新滚动块 → `:599` `渲染可见行(false, 容器高度)` → `:602-609` 刷四个状态文本。

注释 `:586` 说明了意图：每节拍只读一次布局尺寸，并把结果作为参数传给后续函数，避免写入后反复强制重排。
`常量.js:45` 的定义也直接写明：`自动滚动界面间隔 = 50; // 仅限制布局度量、虚拟行和状态文字，不限制滚动帧率`。

前瞻自适应测速（`:488-520`）在这个节拍里算：窗口下移 0.3 视口（`常量.js:64`）→ `:503-506` 用 `js/排版引擎.js:478` 的 `二分句段起点` + 句段负担前缀和取窗口内负担 → `:512-518` 因子夹取并按强度 0.7 做幂映射。

## ④ 停止与并发

停止：`停止自动滚动(原因)`（`:624`）→ `:629 cancelAnimationFrame` → `:630` 把状态置 `null`。
`null` 是幂等性的来源：`:524` 的守卫使任何已排队的下一帧醒来后直接 return，因此多条停止路径（`:617` 文末、`app.js:765-772` 移出、`:726-727` 失焦、`:370/:776` 开弹窗、`:398` 跳转动画钩子）互相竞争是安全的。

并发面：
- **第二条独立 rAF** `执行按键滚动`（Z/X 长按）：`:297` 起、`:332` 自续、`:340` 取消，句柄与主循环分离。
- **滚动事件不驱动渲染**：`app.js:700,:706` 在自动滚动期间让 scroll-rAF 路径直接短路。
- **`js/调度.js` 完全不在这条链路上**（`js/自动滚动.js:1-31` 无该 import，全文仅 `:281` 一处同名字符串）。`调度.js` 只服务索引重建。此前把它当作滚动节流器是误解。

## 风险与缺口

1. **速度反馈环路是开环延迟的**（置信度 high，纯代码顺序）。`:594` 算出的 `密度目标速度` 存进状态，要等**下一帧**的 `:533` 才被读取。因此自适应调速对密度突变的响应滞后 0–50ms（约 0–3 帧）。这是刻意的成本取舍，但意味着：如果将来把 `自动滚动界面间隔` 调大，自适应会明显变钝；调小到 16ms 则等于把 `scrollHeight` 读取搬回每帧，会引入每帧强制重排。**改这个常量必须连带重估二者**。
2. **`:615` 每帧读两个由别处写入的共享字段**：`状态.渲染起点` 与 `状态.行高`。`渲染起点` 只在节拍的 `:599` 里更新，所以非节拍帧复用上次的值——这与 `translateY` 的语义一致（同一渲染窗口内行起点不变），是对的。但它是 `依赖影响分析.md` 里 90 条向上数据耦合中的一条：`行高` 由 L8 的 `js/字体设置.js` 写入，L4 的 `虚拟渲染.js` 与 L8 的 `自动滚动.js` 都读它，改名或改语义不会有 import 错误。
3. **`-1` 哨兵曾被我怀疑会造成视觉跳变，已排除**（置信度 high）。`js/排版引擎.js:463`（`提交行索引`）和 `:501`（`刷新画布尺寸`）都把 `状态.渲染起点` 置 `-1`，而 `状态.js:74` JSDoc 注明 `-1 表示未渲染`；若 `-1` 活到下一帧，`:615` 会算出 `translateY(-行高 - 小数位移)`，即一次整行高的错位。**实测不构成缺陷**：两条失效路径都在同一同步任务内紧跟一次强制渲染——`app.js:265-266` 是 `刷新画布尺寸(新排版); 渲染可见行(true);`，`app.js:245` 的重建回调同样以 `渲染可见行(true)` 收尾，强制渲染绕过 `js/虚拟渲染.js:36` 的窗口未变早退并重写 `:78`。**残余缺口**：`js/虚拟渲染.js:20-22` 在 `状态.行起点列表` 为空时**先于** `:78` 早退，此时 `渲染起点` 会停在 `-1`。只在「空文档/零行」边界可达，影响是一帧行高错位。建议在此处补一行把哨兵归零，或在 `:615` 加 `Math.max(0, 状态.渲染起点)`。
4. **未验证的运行时事实**（本图全部为静态阅读结论）：50ms 节拍是否稳定达成、`#3` 的空文档边界是否真能触发、帧率与掉帧频率。建议的验证动作：在 `:594` 与 `:615` 各插一行 `performance.mark`，跑一本书统计两者的实际间隔分布。
5. **`统计.未入账滚动毫秒`（`:578`）的下游消费链未逐层追完**，只追到 `:581` 的 `安排保存持久化状态()`。这条与本流程解耦，但意味着阅读时长的最终一致性取决于持久化侧的合并逻辑。

## 对上游文档的一处纠正

子代理初稿称 `自动滚动.js:615` 会「二次覆写」`状态.渲染起点/终点`。核实结果相反：`:615` 是**读取**（`translateY(状态.渲染起点 * 状态.行高 - 小数位移)`），全仓对 `状态.渲染起点` 的写入只有 `js/虚拟渲染.js:78`、`js/排版引擎.js:463,501` 三处。本图按核实后的事实绘制。
