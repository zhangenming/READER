## 结论先行

前几轮重构已经解决了最显眼的问题：模块依赖图无环，文本管线中有一批可独立测试的纯函数，长任务普遍会让出主线程，载入、排版、词频和词组分析也都已有取消意识。继续迁移到 React、引入全量状态框架或增加构建工具，当前都不是解决核心问题的必要条件。

现在真正限制项目可靠性和继续演进的，不是文件数量，而是五条边界仍然模糊：

1. **状态提交边界**：全局状态可被任意模块直接改写，没有统一的变更通知、失效传播或保存触发点。
2. **恢复事务边界**：持久化数据一边校验一边写入 CSS、DOM 和全局状态，失败后旧会话也可能被部分改动。
3. **异步任务所有权**：成功路径多半会检查任务是否过期，但异常路径和弹窗实例没有全部遵守同一规则。
4. **数据身份与并发边界**：文本身份只由文件名和长度决定，整个书库又通过一个 `localStorage` 值读改写，没有多标签页冲突检测。
5. **发布边界**：主阅读器依赖服务器目录索引，知识库的源码、输入、生成物和主应用放在同一发布树，但仓库没有声明或校验这些契约。

因此，下一阶段最有价值的工作不是继续拆文件，而是建立几个小而明确的协议：**先校验后提交的会话事务、统一任务令牌、设置描述表、显式状态命令、可靠文本指纹、可观察的持久化结果和静态内容清单。**

本轮没有发现必然导致所有用户数据损坏的 P0 问题；发现 4 组 P1 正确性/数据风险、9 组 P2 结构风险和一批 P3 工程问题。

## P1 · 正确性与数据一致性

### 1. 阅读状态恢复不是事务，损坏记录会留下半恢复状态

**触发条件**：单本书的字号、行高、滚动速度、颜色、排序、阅读位置或关键词记录被旧版本、手工修改、外部脚本或历史缺陷等方式破坏。

**证据链**：

- `js/字体设置.js:863-936` 先清除 18 个左右的 CSS 变量、重置多个全局对象和控件，再从 `js/字体设置.js:937` 开始逐字段校验。后面的任何 `TypeError` / `RangeError` 都会发生在旧会话已经被改动之后。
- `app.js:887-918` 在新书行索引建立前调用上述恢复函数；恢复失败时，新书没有提交，但旧书的视觉设置可能已经被部分重置。
- `app.js:920-940` 先把文本、文件名、索引、关键词和缓存提交到全局状态，`app.js:942` 才恢复阅读位置与关键词。后半段异常时，系统已经处于“新书已提交、内容状态未恢复、错误层显示”的中间态。
- `app.js:981-1006` 只验证关键词列表是数组，没有逐项验证关键词文本、id 类型与唯一性、当前命中索引、配色索引。`文本` 缺失可直接使查找抛错，重复或非法 id 会破坏后续 id 分配，负数/非数值配色会产生无效索引。
- `js/错误提示.js:3-8` 把所有 `RangeError` 都解释成“文本过大”。设置越界也会被误报成 Chrome 安全滚动高度问题。

**影响**：某一本书可能无法打开；更严重的是失败不具备原子性，用户看到的旧书、设置、加载层和内存状态可能不再对应同一会话。刷新页面也未必能自救，因为损坏记录仍会再次参与恢复。

**治理方向**：把恢复分成 `解析 -> 完整校验/迁移 -> 生成会话草稿 -> 一次提交`。校验阶段不得写 DOM、CSS 或全局状态；行索引也应基于设置草稿计算。失败时保留旧会话，明确显示“该书保存状态损坏”，保留损坏快照，并提供显式的“重置该书状态”动作。这里不应静默吞错或逐字段偷偷回退。

**判断**：静态高可信，P1。建议最先处理。

### 2. 异步任务只保护成功提交，没有完整保护异常出口和弹窗实例

**载入与排版**：

- `app.js:294-302` 的 `应用文本(...)` 是跨多个让出点的异步过程；外层 catch 不检查本次载入是否仍然有效。旧任务在失效后抛出的异常仍能调用 `显示文本处理错误`，覆盖新任务的载入界面。
- `js/排版引擎.js:42-47` 给重建任务分配了序号，但 `执行重建().catch(显示文本处理错误)` 的异常出口没有检查序号。旧排版任务的正常结果不会提交，旧任务的错误却仍可提交到全局错误 UI。

**内容弹窗**：

- `js/内容选择弹窗.js:29-55` 只判断“弹窗当前是否打开”，没有记录“是哪一次打开”。第一次打开 A 发起目录读取后关闭，再立即打开 B；若 A 此时完成，它会看到弹窗处于打开状态，并把 A 的目录、统计或错误写进 B 的实例。
- A 和 B 还会共同改写 `状态.文本目录`、`状态.文本字数` 和模块级 `文本字数任务`，这些共享写入同样没有实例归属，因此这不只是提示文字竞态。

**治理方向**：统一使用任务作用域对象，而不是继续增加散落的数字序号。作用域至少提供 `仍有效()`、`提交(fn)`、`报告错误(error)` 和 `取消()`；fetch 同时接 `AbortController.signal`。所有成功、失败、finally 和延迟回调都必须通过同一个作用域提交。弹窗每次打开生成实例令牌，关闭即失效。

**判断**：静态高可信，P1。正常页面运行不会自然覆盖这些窄窗口，需要专门的延迟/失败注入测试。

> 已排除的误报：`app.js:281-286` 的 UTF-8 解码是同步段，且前面 `app.js:277-279` 已检查载入序号；事件循环不能在检查与同步 catch 之间插入另一次载入，因此这段本身不是旧任务竞态。

### 3. 持久化是整库读改写，多标签页可能丢更新，保存失败对用户不可见

**证据链**：

- `js/持久化.js:153-213` 每次保存先读取整个数据库，原地替换当前书记录，再序列化所有书；`js/持久化.js:231` 用单个键覆盖整个数据库。
- 两个标签页都可以从同一旧快照开始。A、B 分别修改不同书时，后写入者可能把先写入者的整库更新覆盖掉。当前没有 `storage` 事件监听、修订号、冲突检测或事务。
- `js/持久化.js:239-242` 捕获配额、隐私模式等写入失败后只写控制台。页面继续表现为设置已经生效，用户刷新后才发现阅读位置或设置丢失。
- 整库 `JSON.stringify` 也让保存成本和单键体积随书籍、关键词数量持续增长，并共同竞争约 5 MB 的 `localStorage` 配额。

**治理方向**：个人静态应用不必立刻引入数据库框架。优先把“索引元数据”和“每本书状态”拆成独立键，给记录增加 schema 版本、修订号和内容指纹；监听 `storage` 事件并在冲突时提示。若继续增长，再迁 IndexedDB。无论存储介质如何，界面都应有可查询的“已保存 / 待保存 / 保存失败”状态，失败不能只存在于控制台。

**判断**：多标签页丢更新是条件性高风险；保存失败不可见是静态确认。整体 P1。

### 4. 文本身份只有文件名和长度，会把旧状态恢复到不同内容

**证据链**：

- `app.js:975-977` 只用 `文件名 + 文本长度` 判断持久化状态是否属于当前内容。同名、同长度的文件被替换后，旧阅读偏移和关键词仍会被恢复。
- `app.js:245-250` 遇到当前文件名直接返回，用户也没有主动刷新同名文件的路径。

**影响**：阅读位置可能跳到无关段落，关键词命中与用户记忆不一致；内容目录缓存的字数也可能继续代表旧文件。

**治理方向**：在读取字节后生成稳定内容指纹（例如 SHA-256），持久化记录绑定 `文件名 + 指纹`。目录服务若能提供 ETag/修改时间，也可用于快速判变，但不能只依赖长度。内容选择器为当前文件提供显式重新载入动作。

**判断**：确定性代码路径，P1；需要同名同长度替换文件才触发。

## P2 · 架构与演进风险

### 5. 全局状态单例没有变更协议，刷新和保存知识散落全仓

`js/状态.js:50` 明确说明“各模块直接读写，无变更通知”。目前可观测后果是：

- `渲染可见行(true) + 更新关键词指示器() + 其他提示/保存` 的组合在约 16 个交互点重复；全仓共有 23 个强制渲染调用。
- `安排保存持久化状态()` 有 35 个调用点，分布在 8 个消费模块。每个突变点都要自己记住何时保存。
- `状态.js` 同时容纳文档会话、渲染状态、用户设置、统计、弹窗缓存和 5 个本应由功能模块持有的计时器；`元素` 又在模块加载期查询约 97 个 DOM 节点。
- 新增一个字段时，没有机制回答“切书时是否重置、是否持久化、会让哪些视图失效、由谁清理”。

这不是要求引入 Redux 或大型响应式框架。最小改法是让业务变化只能通过少量显式命令提交，例如 `提交关键词变化`、`提交排版设置`、`提交新书会话`；命令返回失效标记，由一个 rAF 调度器统一完成渲染、指示器、面板和防抖保存。模块私有计时器回到各自模块。

### 6. 设置没有单一数据源，保存、恢复、继承和 CSS 映射重复维护

同一设置字段至少以四种形态出现：

1. `js/持久化.js:170-213` 的序列化字段。
2. `js/字体设置.js:863-1184` 的默认值、校验、迁移和应用逻辑。
3. `app.js:859-886` 的跨书公共设置继承白名单。
4. 多个 `设置*` 函数和散布的 CSS 自定义属性名。

结果是新增或改名一个设置必须同步修改多个文件，漏一处不会立即报错，只会出现“本次有效、重开失效”或“新书没有继承”的延迟故障。`字体设置.js` 已达 1,184 行，其中约 320 行只是恢复流程，UI、排版动作、颜色、字体列表和持久化协议被绑在一起。

建议用一份设置描述表表达字段名、默认值、校验/迁移、作用域（全局或单书）、是否影响换行、CSS 映射和序列化方式。描述表负责产生“纯设置快照”；DOM 应用与弹窗渲染仍可保持简单函数，不需要做通用表单框架。

### 7. `app.js` 仍承担过多组合职责，`键盘控制.js` 又成为第二个组合根

- `app.js:184-197` 在启动时直接创建定时器、Observer、绑定所有功能并载入文本；`app.js:313-666` 集中绑定大量 DOM、window 和语音事件。
- `应用文本` 仍是约 210 行的五阶段管线、设置恢复、状态重置、索引提交、内容恢复、渲染和日志总编排。`app.js:920-937` 是一份隐式的“切书重置清单”。
- `js/键盘控制.js` 约 535 行并导入 12 个模块。导航核心 `执行导航跳转` 位于键盘层，导致正文交互、关键词手势等非键盘模块反向依赖键盘控制；键盘层还直接打开三个弹窗。

组合根本身可以大，但不应成为业务能力的唯一入口。建议把导航原语迁到 `导航.js`，弹窗暴露命令，由键盘映射表调用；把新书装载编排成有明确输入/输出的“构建会话”和“一次提交”。`app.js` 最终只负责初始化功能、连接命令与界面、管理顶层生命周期。

### 8. 虚拟渲染器混入语言规则，内容语义无法独立验证

`js/虚拟渲染.js:175-275` 的热循环除 DOM 构建外，还承担：

- “我/他/你”替换为 W/T/N。
- “的/了”特殊字形、“不”字否定叉。
- 人称代词组合判断。
- 约 50 字符的关系字字面量。
- 两字关系连词的前后邻接分类。

这些规则无法在不构造 DOM 的情况下直接验证，调整词表也会触碰性能敏感的渲染循环。项目已有 `搜索.js` 和 `文本管线.js` 的纯函数先例，可以抽出 `计算字符标注(文本, 起点, 终点)` 或预计算标注索引，让渲染器只消费类名和展示文本。

### 9. Unicode 的“汉字”定义不一致，阅读负担会漏算一部分字符

- `js/文本工具.js:29-36` 的 `是汉字()` 覆盖 Unicode Han，包括兼容汉字和补充平面字符。
- `js/文本工具.js:39-46` 的 `是阅读字符码()` 只接受 BMP 的扩展 A、基本汉字和 ASCII 英数。
- `js/文本管线.js:423-430` 又按 UTF-16 code unit 调用 `是阅读字符码()` 构建自适应滚动负担。

因此兼容汉字、扩展 B 及之后的 Han 字符可进入词频/汉字语义，却不会计入句段负担，补充平面字符还会被拆成两个代理项跳过。自适应滚动剩余时间和速度模型会对含生僻字文本产生系统性低估。

应统一为基于 code point 或字素的分类函数，并让词频、负担、搜索边界共享同一套 Unicode 语义。这个问题是确定性代码路径，现有测试没有覆盖补充平面汉字。

### 10. 关键词标记与查找弹窗拥有两套不同的命中语义

- `js/关键词.js:216-247` 每次命中后只前进一个字素，因此允许重叠命中；现有 `tmp/verify-keyword-search.mjs` 已断言 `哈哈哈` 查 `哈哈` 得到 `[0, 1]`。
- `js/查找弹窗.js:205-229` 每次前进整个关键词长度，因此同一输入只得到 `[0]`。

这会让同一词在临时查找和正式关键词中的数量不同，上下一个导航与词组分析也可能基于另一组位置。应由一个纯查询原语统一字素边界、排除前缀和“是否允许重叠”选项；产品只需明确一次默认语义。

### 11. 错误可观察性不一致，部分失败只留在控制台

- 保存失败：`js/持久化.js:239-242` 只有 `console.warn`。
- 词组分析失败：`js/查找弹窗.js:397-399` 只有 `console.error`，分析面板没有失败状态或重试动作。
- 语音协议错误：`语音订阅.js:166-172` 静默丢弃非法 JSON，既没有日志，也没有错误计数或最近错误。
- 文本处理错误虽有 UI，但所有 `RangeError` 共用错误文案，丢失了错误类型语义。

建议定义小型错误分类，不必做日志平台：错误至少包含阶段、任务/文件身份、是否可重试、面向用户的状态和原始 `cause`。协议损坏、保存失败和恢复失败都应可见且可追踪；高频可预期事件再做限流，而不是静默吞掉。

### 12. 内容目录依赖服务器目录索引，静态发布契约没有编码

`js/内容选择弹窗.js:135-171` fetch `./txt/`，再解析服务器生成的 HTML 目录页。Python `http.server` 会提供目录索引，所以本地使用正常；很多静态托管、CDN 和安全配置不会列目录，此时主书仍可能打开，但内容选择器必然失败。

如果产品永远只在当前本地服务器运行，这是一项已知约束；若要部署，应该生成 `txt/index.json` 或其他显式清单，并在测试里验证清单和文件一致。部署需求不能继续隐含在服务器偶然行为里。

### 13. `daming1566-kb/` 的源码、输入与生成物边界不清

- `daming1566-kb/docs/` 与 `chapter_md/` 共 134 个生成文件全部入库，但没有 CI 或本地门禁验证重新构建后无漂移。
- `daming1566-kb/scripts/build.py:20-24` 的默认输入是开发者机器绝对路径，换机器必须知道并设置私有环境变量。
- `build.py:156-168,270` 对显示文本使用了 `html.escape`，但实体规范名直接进入 `href` 和 `id`，没有统一的 URL/属性编码。当前实体表是可信输入，所以不是紧急注入漏洞；它仍是生成器对未来数据的脆弱契约。
- 根静态服务器同时暴露主阅读器和这个独立知识库，但二者没有共同构建、共同版本或明确独立发布的声明。

不一定要拆仓库。最低限度是把它声明成独立子项目：输入路径可移植、生成命令可重复、输出有漂移校验、实体 slug 有唯一编码函数，并明确根目录发布是否包含它。

## P3 · 测试、可访问性与工程卫生

### 14. 测试覆盖的是“正常成功路径”，没有锁住上述事务与错误不变量

现有五组测试覆盖模块图、持久化迁移、词组提取、关键词字素和布局竞态，价值明确，但还缺少：

- 每个持久化字段损坏时，旧会话保持不变且错误可见。
- 旧载入/旧排版任务失败时，不得覆盖新任务 UI。
- 内容弹窗“打开 A、关闭、打开 B、A 后完成”的实例隔离。
- 同名同长度文本替换、多标签页快照冲突、存储配额失败。
- 查找与关键词的统一重叠语义、补充平面 Han 字符。
- `创建行索引` 的换行边界和字体/字号组合，而不只是竞态提交。
- `状态.js` 约 97 个 selector 与 `index.html` 103 个唯一 id 的静态交叉校验。
- `daming1566-kb` 重新构建后的生成物漂移。

测试文件放在 `tmp/`，与截图、临时 HTML 和其他杂物混放，但 `npm test` 又把它当正式资产。应迁到 `tests/` 或 `verify/`，让“可删除临时目录”和“发布门禁”不再同名。

### 15. 弹窗与动画的可访问性模型不统一

- 查找、上下文、词频和内容选择使用原生 `<dialog>`；字体设置使用 `div[role=dialog]`（`index.html:361-369`），需要自行保证焦点圈、背景 inert、Escape 和焦点恢复。
- 字体、查找和词频关闭后固定聚焦正文，而不是恢复触发元素；不同弹窗行为也不一致。
- 正文字素全部 `aria-hidden=true`，每行用原始文本 `aria-label` 补回可读内容。这能避免 W/T/N 视觉替换污染朗读，但关键词命中、当前命中和其他语义标注不会进入辅助技术信息。
- CSS 的 `prefers-reduced-motion` 只关闭部分入场动画；`js/跳转动画.js:210-261` 的滚动动画和粒子流程不读取该偏好。

建议统一使用原生 dialog 或一个经过测试的 modal 控制器，记录并恢复触发元素；为当前关键词/命中提供独立的 live status，不要把所有视觉装饰塞进行文本；JS 动画也尊重 reduced motion。

### 16. 顶层生命周期只能启动，不能销毁

`app.js:182-197` 模块加载即启动，创建永久 interval、ResizeObserver 和大量全局监听；`语音订阅.js` 也有常驻 WebSocket 与重连计时器。当前单页、整页刷新模型下不会重复初始化，所以这是条件性风险，不是当前泄漏证据。

但它让浏览器集成测试、热重载、嵌入其他页面和同文档重新初始化都很困难。建议让 `启动()` 返回 `销毁()`，由各功能注册函数返回清理函数；Observer、计时器、动画帧和 WebSocket 都纳入同一生命周期。

### 17. 仓库卫生仍会增加噪音和不可重复性

- 没有 `.gitignore`；`.DS_Store`、`.reasonix/`、`.workbuddy/`、`.openclaw/`、`.claude/` 等个人工具状态已经入库，存在噪音、隐私和跨机冲突风险。
- `js/常量.js:2-3` 默认书名硬编码为一个具体下载文件名。文件缺失时启动直接失败，没有从内容清单选择首本或显示空库状态。
- `语音订阅.js` 被 `index.html` 无条件加载；不用语音时也会持续连接并每 5 秒重试。查询参数可改地址，却没有显式关闭开关。
- `搜索.js`、`统计展示.js`、`面板.js`、`文本管线.js` 和 `tmp/verify-模块图.mjs` 权限是 600，其余源码多为 644。
- `重构适用性评估.md` 仍写 `app.js` 约 1,425 行、23 模块；实际为 1,037 行、24 模块。结构事实再次漂移。
- `读取持久化数据()` 没有生产调用者，只有测试使用；若严格读取 API 不再是产品契约，应删除或明确标为测试/诊断接口。
- `设置文本` / `设置属性` 是通用 DOM helper，却位于 `虚拟渲染.js:602-612` 并被其他视图模块反向引用，归属不清。

## 建议的目标形态

不换技术栈也可以把关键边界收紧为下面这条链：

```text
DOM / 键盘 / 语音事件
          |
          v
      用例命令层  ------> 任务作用域（取消、错误归属、实例令牌）
          |
          v
  纯会话草稿（文本 + 设置 + 索引 + 恢复数据）
          |
       完整校验
          |
          v
     一次提交状态
       /       \
      v         v
视图失效调度器   持久化队列（版本、指纹、保存状态）
```

建议把状态按所有权拆成四类，而不是继续扩大一个对象：

| 状态域     | 典型内容                             | 生命周期                     |
| ---------- | ------------------------------------ | ---------------------------- |
| 文档会话   | 文本、行索引、引文、关键词、阅读位置 | 每次成功切书一次替换         |
| 用户设置   | 字号、字体、颜色、速度、开关         | 经过设置命令提交，可跨书继承 |
| 运行时     | 计时器、动画帧、任务令牌、悬停/拖拽  | 模块私有，关闭或销毁时清理   |
| 统计与存储 | 今日/总时长、记录修订、保存状态      | 显式结转和持久化             |

关键原则是“谁拥有，谁清理；先构建草稿，再提交；提交一次，派生刷新一次”。

## 分阶段处理顺序

### 阶段 0：先建立失败路径门禁

新增损坏状态、旧任务异常、弹窗跨实例、同名同长度文本、Unicode Han、配额失败和多快照冲突测试。把正式测试迁出 `tmp/`，加入 DOM id 与知识库生成物校验。此阶段不改变产品行为。

**完成标准**：每个 P1 都至少有一个当前会失败的回归测试；测试能证明失败时旧会话未被改写。

### 阶段 1：恢复事务与任务作用域

先做纯设置解析/校验和关键词逐项校验，再构建会话草稿；最后一次性替换文档会话并应用 DOM。同步统一载入、排版、分析和弹窗实例令牌，所有异常出口检查所有权。

**完成标准**：任意字段损坏、任意阶段取消或抛错，都只能得到“旧会话完整保留”或“新会话完整提交”两种结果，不存在中间态。

### 阶段 2：收敛状态突变、刷新和设置描述

引入少量业务命令和失效标记，替换 16 处重复刷新组合与 35 个手工保存触发点；建立设置描述表，拆出字体弹窗外壳、设置域和恢复域；把计时器迁回所有者模块。

**完成标准**：新增一个设置字段只需在描述表和对应 UI 各声明一次；新增一个关键词动作不需要手写渲染、指示器和保存三连。

### 阶段 3：修正身份与持久化模型

加入文本内容指纹和显式重新载入；拆分每书记录与索引元数据，增加 schema 版本、记录修订、跨标签页通知和保存状态 UI。只有数据量确实超过 `localStorage` 的合理范围时再迁 IndexedDB。

**完成标准**：同名同长度替换不会恢复旧状态；两个标签页修改不同书不会静默互相覆盖；保存失败在当前页面可见并可重试。

### 阶段 4：整理领域与发布边界

抽离导航原语和内容标注纯函数，统一搜索/Unicode 语义；内容目录改显式清单；声明 `daming1566-kb` 子项目边界并加入可重复构建；最后处理 dialog、reduced motion、teardown、`.gitignore`、文档统计等 P3。

**完成标准**：渲染器不再定义语言词表；静态服务器不提供目录索引时内容选择仍可用；知识库在另一台机器能从声明的输入完整重建且 git 无差异。

## 不建议现在做的事

- 不建议为了“有状态管理”迁移 React/Vue。当前问题是提交协议缺失，换框架不会自动修复恢复事务、文本身份和存储并发。
- 不建议先按行数机械拆 `app.js` 或 `字体设置.js`。没有先定义所有权时，拆文件只会增加跨模块调用。
- 不建议对损坏单书状态做静默默认值回退。应先完整校验、保留原始快照、明确提示并由用户选择重置。
- 不建议把每种竞态再发明一种序号。统一任务作用域比继续累计局部习语更容易验证。

## 本轮排除的疑点

1. **UTF-8 同步解码不是当前竞态**：任务检查与 decode/catch 之间没有 await。
2. **未确认当前存在字体加载后行索引漂移**：`styles.css:885-893` 把非西文字盒固定为 `1em`，排版引擎也按字号计算；西文使用独立系统字体并由 Canvas 测量。若未来把 `--西文字体` 换成异步 webfont，才需要 `document.fonts` 参与重建协议。
3. **依赖图没有环**：当前模块拆分成果是真实的；问题主要在共享可变状态和运行时协议，不在 import 图本身。
